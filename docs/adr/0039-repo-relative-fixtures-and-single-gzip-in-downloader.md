# ADR-0039: Repo-relative fixture urls and single-gzip support in the downloader

- **Status**: Accepted
- **Date**: 2026-07-24

## Context

Testing a change in a worktree needs a dataload of a *few* mapping sets, not the full corpus (OLS's
whole `sssom.tgz` plus every Mapping Commons registry). The pre-existing worktree config
(`oxo-config-test.json`) reached for a small slice with `file:///home/<user>/ebi-dev/oxo2/sssom/…`
absolute paths — machine-specific paths that lived *outside* the repo, so the config did not travel
to another checkout, another developer, or CI. OLS only publishes per-ontology SSSOM as members of
one bundled `sssom.tgz`, so there is no cheap per-ontology URL to fetch instead; the pragmatic way to
pin a handful of ontologies is to commit trimmed slices into the repo. But the downloader had two gaps
that blocked a committed, portable test config:

1. A relative `url` did not resolve. `HTTPDowloader` classified a local file by
   `url.startsWith("file://") || new File(url).exists()`, and `new File(relative).exists()` is
   evaluated against the Nextflow process working directory — not the checkout — so an in-repo path
   like `testcases/worktree/efo.sssom.tsv` was treated as a remote URL and failed. The config is also
   rewritten per-registry into the work dir before the JAR reads it (`downloadMappings.nf`), so the
   downloader cannot recover the original config location on its own.
2. A single-member gzip (`*.tsv.gz`) fetched by a plain `url` was saved compressed and then silently
   ignored: `HTTPDowloader` only unpacked `.tgz`/`.tar.gz`, while the downstream `sssom2json.nf` globs
   `**.tsv`. (The Mapping Commons *registry* downloader already gunzips its `.gz` entries; the
   plain-`url` path never got the same treatment.)

## Decision

Teach the downloader to consume both. `DownloadMappings` gains an optional `--base-dir`; a relative
local `url` resolves against it, `file://` and absolute paths are unchanged, and remote (`http`/`https`/
`ftp`) urls are untouched. `downloadMappings.nf` passes `--base-dir` = the directory holding
`$OXO2_CONFIG`, so a relative `url` in a config means "relative to that config file". A plain-`url`
download whose name ends in `.gz` (but not `.tgz`/`.tar.gz`) is gunzipped to its inner `.tsv` after
download, mirroring the registry downloader.

The committed `oxo-config-test.json` uses this: three trimmed OLS ontology slices
(`testcases/worktree/{efo,mondo,uberon}.sssom.tsv`, regenerated by `testcases/worktree/trim-fixtures.sh`)
referenced by repo-relative `url`, plus the `uniprot` Mapping Commons set fetched live by URL.

## Consequences

- A worktree dataload of a few sets is now fully in-repo and portable — no machine-specific paths, no
  external fixtures. Every checkout and CI runner resolves the same relative fixtures.
- The trimmed OLS slices keep every strong (semantic) mapping row and a bounded sample of the weak
  `hasDbXref`/`subClassOf` rows, preserving cross-set inference overlap (MONDO↔EFO exactMatch) while
  staying ~0.5 MB total. They are a *snapshot* of an OLS export; `trim-fixtures.sh` regenerates them
  from a full export when refreshed.
- Any `.tsv.gz` mapping set can now be ingested by a plain `url`. This deliberately does **not** put
  the biopragmatics `priority.sssom.tsv.gz` (Zenodo record 15826794) into the default test config: it
  is 2.6M `skos:exactMatch` gene rows (569 MB decompressed) with no overlap with the OLS test
  ontologies, and one giant exactMatch component — exactly the cross-set closure explosion
  [ADR-0017](0017-cross-set-inference-corpus-component-size-guard.md) guards against but was never
  built. It can be added as a one-line `url` entry when a large/gene set is actually wanted, at the
  cost of a much heavier load (raise `SOLR_HEAP`).
- `--base-dir` is optional; when absent (e.g. the standalone `downloadMappings.sh`) a relative url
  falls back to the working directory, the pre-ADR behaviour. Existing configs use absolute/remote
  urls and are unaffected.
